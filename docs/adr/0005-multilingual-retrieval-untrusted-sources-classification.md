# ADR 0005 — Mixed-language retrieval, document authority, and classification proposals

- **Status:** PROPOSED — architecture decision for evaluation; **not an implementation or release approval**
- **Date:** 2026-10-25
- **Scope:** AKP S2 retrieval and later ingestion/classification and agent-action security
- **Depends on:** [ADR 0001](0001-canonical-corpus-and-derived-projections.md), [ADR 0002](0002-review-and-publication-isolation.md), [ADR 0004](0004-core-product-scope-and-simplification.md), [core redesign spec](../architecture/core-redesign-execution-spec.md), [S2 experiment ledger §39–40](../architecture/s2-semantic-experiments-and-integration-ledger.md)
- **Explicitly unchanged:** immutable SOURCE, approved KNOWLEDGE, derived indexes, effective ACL and revision binding, LAYERED admission design, independent action authorization, S2 OPEN / E5 SHADOW / S3–S5 BLOCKED, PR #38 draft/unmerged

## Context and evidence-based problem

AKP must let Spanish-speaking software teams ask in Spanish about English technical sources, and ask in English about Spanish process documents, without obliging each user to pre-sort documents or pick a mandatory search language. The existing system already contains multilingual E5 retrieval, reciprocal-rank fusion, `OpenAICompatibleQueryTranslator` and a configurable query transformer in the **same** API search route; [existing research](../architecture/evidence-admission-research.md) cites RAGFlow's source implementation of cross-language query legs. Neither translating the original SOURCE nor creating a second retrieval engine is necessary.

A fresh owner-AI source-bound HTTP evaluation (§39) registered 12 cases from three English technical publishers. Both lexical and E5 returned authorized candidates for the correct source family on the Spanish positive questions, but admitted **0/3** positive ES cases. Of 213 candidate observations, **all** used `DETERMINISTIC` admission (semantic reader absent), so this **does not establish LAYERED failures** or that E5 alone caused the abstentions. The split EN vs ES is a meaningful **hypothesis**, not a population-level causal claim. We must distinguish source detection, retrieval, admission, citation, and answer accuracy before tuning any gate.

A second concern is the integrity boundary: a newly uploaded document, signed connector payload or approved topic folder is **source data**, not an instruction issuer for the agent. A correct cryptographic quote may still be false, superseded, malicious or irrelevant. In particular, a document that claims “send payment to account X” cannot grant an agent banking authority, even if it is retrieved, correctly cited or classified as a billing procedure. OWASP documents prompt injection and RAG poisoning in retrieved material, and recommends external tool permissions and output/action screening rather than prompts or regex alone.

A third concern is classification on ingestion: a stable Markdown hierarchy and per-vault KnowledgeProfile are useful contractual schemas, **not** evidence that an arbitrary uploaded PDF/DOCX/image has been correctly organized. Classification accuracy, source trust, lifecycle, language, business authority and permitted actions are distinct concepts.

## D1 — Language is retrieval metadata, not a mandatory user filter

**Accept for future implementation/evaluation:** Preserve the original source bytes, exact offsets and language(s) on immutable source/projection and index units. Permit `en`, `es`, `mixed` and `undetermined` at the metadata level (suggested schema, **not** a migrated contract). Detect language per document **and, where mixed, per searchable section**, retaining detector/model version and uncertain state. Never infer language from a folder name as a security or truth claim. Preserve technical identifiers, commands, versions, negations, thresholds, and citations verbatim.

Keep the **original question leg**. On a mixed-language corpus use a **bounded, opt-in, language-aware query expansion** through the existing `QueryTransformerPort`: source-language translations for the known corpus languages (locally pinned provider for private data), plus original lexical/vector legs, de-duplication and existing RRF ranking. Each translated query is an untrusted _search proposal_, not a new user instruction, a source document or proof of answerability. Any variant that drops/changes source-critical numbers, identifiers, conditional operators or negation must be rejected or marked uncertain; original query remains usable if translation fails. Enforce the **same ACL, tenant/vault, lifecycle and revision** on every leg and deduplicated hit.

Use E5/other multilingual embeddings for candidate retrieval and optional **language-specific lexical analyzers** only where experiments show a gain; prefer one scoped mixed corpus with per-language indexed projections over parallel authoritative corpus copies. Do not automatically translate/store original documents as new canonical evidence. Respond in the user's interaction language by default, but retain source-original quotes and locators; a UI display language preference may be offered later, **never** a prerequisite for finding cross-language documents.

**Existing implementation to reuse:** `packages/retrieval/src/query-translation.ts`, `query-transform.ts`, existing `queryKnowledge`, RRF, `apps/api/src/runtime-config.ts` and `server.ts`. The translator is currently opt-in via configured model/base URL/languages. Do not promote it, E5 or a new analyzer to production until paired evidence passes the S2 gates. Audit external translation provider data-residency before enabling it on private queries.

**External documentation:** [Azure AI Search multi-language indexing](https://learn.microsoft.com/en-us/azure/search/search-language-support); [Azure AI Search indexing and filterable fields](https://learn.microsoft.com/en-us/azure/search/search-how-to-create-search-index); [RAGFlow cross-language search](https://ragflow.io/docs/v1.0.0-rc2/chat_configuration). These are documented approaches, **not transferred AKP metrics**.

## D2 — Preserve the authority boundary when retrieved content reaches an agent

**Decision:** Privileges come exclusively from authenticated principal/session, server-owned policy, API tool definitions and current revision/ACL; **not** from text in a retrieved source, a search result, a compiler-generated claim or a KnowledgeProfile category. Classify an instruction-like sentence inside a document as **source subject matter**. The model may quote it accurately or compare it with other documents, but must never promote it into a system/developer instruction or an executable tool policy.

**Separate two threat classes**:

1. **Indirect prompt injection:** a document says to ignore system rules, leak private content, invoke a tool, forge a reviewer, alter permissions or submit a payment. Block instruction promotion; never pass external text into privileged tool definitions or higher-priority prompt roles.
2. **False/poisoned business assertion:** a document looks like a genuine invoicing procedure but contains incorrect beneficiary details, invented rates or outdated approval workflows. A prompt-injection detector may find nothing because the text resembles ordinary facts. Retrieval relevance/quote SHA/classification do **not** establish business truth. Resolve against a separate authoritative current policy/beneficiary registry with owner-governed lifecycle; surface source conflict or unverified status instead of asserting a reliable payment instruction.

**Required action boundary:** For monetary transfers, account/beneficiary changes, payments, access changes, secret/export/network disclosure, Git publication and other side effects, the **executor** must enforce service-side explicit action permissions, typed parameters, verified current business-record identity, action-specific approval where required, idempotency and audit. Source text cannot authorize a transfer or nominate a destination account; even an `APPROVED KNOWLEDGE` document cannot bypass the transaction system. If these controls are missing, do not expose that mutation as an autonomous tool. For read-only answers, distinguish “the document states X” from “verified policy authorizes X”; when contradictory or stale, indicate the uncertainty with citations and deny unsupported transactional instructions.

**Defense in depth, not a single LLM classifier:** Bound the original excerpt with explicit untrusted provenance, structured content roles and exact SHA/UTF-16 spans; do not mingle with tool/system messages. Screen ingestion **and retrieved context** for suspicious instruction-bearing material, including obfuscation, metadata and multi-chunk attacks; high-risk findings flag/quarantine **as policy permits** rather than delete the immutable original. A specialist classifier is advisory and may have false positives; analyze benign how-to/software instructions as controls. Independently validate outbound claims, citations and downstream tool arguments. Guardrails do not confer trust, and hostile documents may evade them.

**Current proof gap:** The repository already states this boundary in the core spec/threat model and a `ContextPacket` regression checks `requiredActions` plus absence of `permissions`/`toolPolicy`. This establishes packet _structure only_, **not** that an adversarial retrieved document cannot redirect a deployed writer/agent or side-effect tool. A signed connector webhook verifies sender/bytes, **not accuracy or agent authority**. No deployed payments tool is inferred from the user's example.

**External controls:** [OWASP RAG Security](https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html), [OWASP LLM Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) and [OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

## D3 — Classification is advisory organization, never automatic promotion to authority

**Decision / candidate pipeline, NOT YET IMPLEMENTED:** `uploaded immutable original → parse/layout/OCR with preserved page/table/span locators → policy/ACL and provenance check → multilingual embedding & indexed class examples → candidate knowledge kinds from the **active versioned KnowledgeProfile** → optional constrained classifier (model/provider interchangeable) → structured multi-label proposal + calibrated uncertainty → validation/review policy → governed metadata publication / indexed virtual navigation`.

Do **not** replace each tenant's profile by a fixed universal directory hierarchy. Use the **existing** `KnowledgeProfileV1`, revision hashes, allowed knowledge kinds, review policies and compiler contracts as the candidate taxonomy; proposals for an undeclared class or absent owner policy become `UNCLASSIFIED`/pending and cannot silently invent new durable schemas. Separate at least these proposed dimensions rather than collapsing into one model label: (a) physical artifact/layout type (PDF/MD/scan/table/etc.); (b) semantic knowledge kind and optional multiple topics; (c) detected language(s); (d) current source authenticity, provenance, lifecycle and review **set outside classifier**; (e) user/space/vault permissions and sensitivity **set outside classifier**; (f) suspicious-content risk annotations **not equivalent to proven malice**.

A suggested classification record should retain original artifact/revision hash, active profile revision/hash, **candidate IDs and scores/ranks, model/prompt digest**, selected label(s), confidence margin, language scope, original evidence spans, `UNKNOWN`/other outcome, and override/approval history. These fields are **proposed contract requirements**, not present persisted tables. No confidence score automatically upgrades `MACHINE_SUPPORTED` to `HUMAN_REVIEWED`, assigns write ACL, changes financial beneficiary or edits canonical Git. Initially offer non-destructive organization / search facets and an approval queue; avoid moving files in source vaults automatically. Accepted metadata changes must trigger revisioned projection/index invalidation and be reversible/auditable.

**Provider and 77% claim:** The user-suggested `embeddings → candidate categories → Llama 4 Scout → label` is a plausible **comparison arm**, not a selected default. Meta's publicly listed Llama 4 Scout benchmarks cover diverse reasoning, document QA and multimodal tasks, **not evidence of 77% accuracy on AKP's custom tenant taxonomy**. Keep provider-neutral interface and compare simple deterministic/profile baselines, multilingual nearest-class embeddings, a locally available constrained classification model, and Scout _only if_ license, hosting, data residency, cost and frozen model version fit. Build an AI-owner DEV suite and a **new disjoint evaluation** with class imbalance, mixed language, abstention, multi-label accuracy, stability across taxonomy revisions, false authority upgrades and injection/poisoned examples. Report **macro/micro F1, per-class precision/recall, confusion matrix, abstention/coverage, review workload, latency/cost**, not a single opaque “accuracy 77%”.

**External documentation:** [Azure Document Intelligence classification](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-classifier?view=doc-intel-4.0.0), which reports document types, page ranges, confidence and supports an “other” class/threshold; [Meta Llama 4 published model benchmarks](https://dev.meta.ai/llama/models/llama-4), which do not establish AKP classification performance. Do not duplicate the S1 extractors/compilers as a new standalone backend.

## D4 — Release order, evidence and deliberately deferred choices

1. **S2 FIRST — multilingual diagnosis using existing architecture.** Add opt-in trace fields/measurements around language detection, translation variants, vector/lexical candidate source language, ACL + source SHA, dedup/RRF, the **actually active** deterministic vs LAYERED reader, quote/citation, and complete answer. Prospectively freeze new source families and tasks with EN→EN, ES→ES, EN→ES, ES→EN, mixed-language pages, technical identifiers, negated/polarity and missing-answer cases. Compare unchanged original-only retrieval to translated query legs and current E5; report _question-level_ support/abstain, negative false admission, cross-language recall and latency with the **same real permission/revision**. Do not tune/relabel on exposed §37–39 cases.
2. **SECURITY CRITICAL — across content → tool boundary.** Inventory real HTTP/Web/MCP/agent callers that consume ContextPackets, existing source approval controls and every executable tool. Add isolated red-team corpus for both malicious _instructions_ and believable but false _business facts_, with benign procedural documents. Prove no unauthorized tool execution/exfiltration, denial of unverified payments, ACL/revision integrity, source-conflict disclosure and low false-positive rejection of harmless technical docs. Distinguish model refusal from **executor-enforced denial**.
3. **CLASSIFIER FOLLOW_UP — contract and shadow proposals only after source/index fidelity.** Define versioned proposal/status and profile migration; instrument (do not grant privileges) classification candidates and confidence on a new corpus. A class can improve retrieval facets but must not become an authorization or truth shortcut. Reuse worker/compiler and existing API/approval infrastructure.
4. **LATER — promote only when demonstrated.** Any new mode/proposal must pass independent-like source-disjoint AI DEV then independently governed release evidence under current protocols, without worsening answerability or authorization; the owner may separately version governance, but retroactively naming self-judged metrics “independent human” is never evidence.

**Deliberately undecided pending measurements:** Default query-translator model/provider and languages inferred vs declared; per-language indexing/analyzer strategy; language detection thresholds and cross-language lexical fallbacks; default LAYERED reader; class taxonomy UX and confidence cutoff; use of Scout or any cloud classifier; workflow destinations requiring approval. No provider installation, schema migration or production action enabled in this ADR.

## Rejected shortcuts

- Mandatory user-selected language, segregated English/Spanish source folders or translation that replaces SOURCE bytes.
- Fixing ES recall via source-type/keyword exceptions or admitting all E5 exploratory hits.
- Promoting a search ranker/classifier or model agreement into source truth, ACL authority or tool permission.
- Treating harmless procedural descriptions as intrinsically malicious; keyword-only injection blocking.
- Using a single reported model accuracy number as justification for a default.
- Inventing a parallel classifier service, alternative durable schema, or bypassing KnowledgeProfile/managed Git review.

**Governance:** This ADR establishes a **proposed, documented decision and work plan**. None of D1/D2/D3 is claimed fully implemented, and S2 remains OPEN, E5 SHADOW, S3–S5 BLOCKED.
