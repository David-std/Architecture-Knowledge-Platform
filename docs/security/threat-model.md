# Threat model

The local deployment uses application-layer authorization and explicit trust boundaries. The controls below describe the maintained product behavior; residual risks are intentionally stated rather than hidden behind a generic “production ready” claim.

- **Cross-space read/write — API/DB.** Permission-specific space lists, membership roles and path prefixes are evaluated together and exercised by integration tests. Residual risk: PostgreSQL RLS is not the primary boundary, so an application defect remains possible.
- **Local file disclosure — ingest/project scan.** Inputs are resolved to canonical real paths, constrained to registered allowlist roots and checked as files or immutable repository commits where appropriate. Residual risk: broader configured roots increase the operator-approved access surface.
- **SSRF — ingest/extractor.** HTTP(S) ingest is rejected; remote content must first become a captured local snapshot. Residual risk: a dedicated URL-capture service is not part of the current product scope.
- **Path traversal — Git drafts.** Proposed Markdown paths are normalized, restricted to allowed prefixes and written through isolated worktrees. Residual risk: the Windows device-name and symlink adversarial matrix can be expanded further.
- **Review escape — concurrent drafts.** Per-review worktrees, publication locks, optimistic base checks and regression tests isolate draft publication. Residual risk: Git and PostgreSQL use compensation and reconciliation rather than a distributed transaction.
- **Mutable raw substitution — worker/object store/extractor.** Raw objects use content-addressed keys; the worker rehashes bytes and the authenticated extractor verifies the expected SHA-256. Residual risk: privileged MinIO credentials can still delete objects and Object Lock is not enabled by default.
- **Extractor impersonation — worker/extractor.** A shared secret, loopback binding, bounded uploads and source-hash verification protect the local boundary. Residual risk: this is not mTLS or per-job workload identity.
- **Oversized upload or temporary-storage exhaustion — extractor.** Configured byte limits, chunked streaming and temporary-file cleanup bound individual extraction requests. Residual risk: aggregate concurrent-volume quotas are not implemented.
- **Default credential — authentication.** The bootstrap credential is revoked and provisioning requires a strong non-default value. Residual risk: local secret rotation remains an operator responsibility.
- **Session theft/CSRF — Web/API.** Browser access uses random opaque sessions, hashes at rest, HttpOnly/SameSite cookies, expiry, revocation and a CSRF header. Residual risk: OIDC, MFA and device assurance are outside the current local scope, and XSS defenses still require maintenance.
- **Malformed identifier or error leakage — API/DB.** Identifier validation returns structured client errors without database detail. Residual risk: maintained authorization and error tests must continue to run after boundary changes.
- **Prompt injection or malicious HTML — extracted content/Web.** Extracted material has no publication authority, active HTML is sanitized, React output is escaped and canonical changes require human review. Residual risk: the adversarial corpus is intentionally bounded and indirect prompt-injection techniques continue to evolve.
- **Derived import metadata — importer/source input.** Fields that resemble authoritative identity, including `__akp_import_identity`, are untrusted source input. The importer reconstructs identity as a projection and checks historical metadata against the observed ID, path, type and content hash where available; derived metadata cannot change the real document identity. Residual risk: missing source facts cannot be inferred safely.
- **Caption or locator overreach — extracted artifact/retrieval.** A preserved table or figure caption and its locator are source material and provenance, not authorization or truth. Caption content cannot donate support to another table row, cell or neighboring unit; row and cell evidence still requires its own bound source span.
- **Secret commit — repository.** `.env`, backups and private reports are ignored and CI performs deterministic secret scanning. Residual risk: the scanner is heuristic rather than managed DLP.
- **Backup disclosure or corruption — operations.** Backup sets exclude secrets, record per-file SHA-256 values and are exercised through isolated restore verification. Residual risk: encryption, WORM storage and remote replication remain deployment responsibilities.
- **Dependency or image drift — supply chain.** Lockfiles, frozen installs, audit/peer gates and pinned runtime/model revisions constrain dependency drift. Residual risk: CI actions and container base images are not all pinned by immutable SHA or digest.
- **Audit tampering — API/DB.** Audit viewing is scoped and relevant mutations emit audit events. Residual risk: append-only behavior still depends on database-role discipline.

All services bind to `127.0.0.1` by default. Tokens are never accepted in query strings. The platform is not approved for direct internet or hostile multi-tenant exposure without additional controls such as database-enforced isolation, managed identity and secrets, encrypted recovery, stronger extractor identity and a broader adversarial test program.

## Security design gap — retrieved-source instruction and corpus poisoning (2026-10-25)

**Threat is not limited to user input.** A legitimate user can ask a harmless question while attacker- or error-controlled source material enters later through import, a connector, compiled derived knowledge, retrieval or a shared vault. A signed webhook, original-byte hash, source citation, document type label, `HUMAN_REVIEWED` test fixture flag or entity embedding match is not evidence of the _truth_ of the statement, nor permission to execute it. The current structural ContextPacket regression treats injection strings as untrusted content but **does not validate a live agent's action boundary**. [ADR 0005](../adr/0005-multilingual-retrieval-untrusted-sources-classification.md) records the proposed controls and the exact missing proof.

Two **separate** scenarios must be covered by future integration and adversarial tests:

- **Indirect instruction injection** in retrieved Markdown, PDF, table notes, code comments, metadata, connector outputs or multi-chunk narratives attempts to override agent role, reveal secrets, change permissions, forge an approval or call privileged tools. Existing prompt delimiters and advisory classifiers are not a sufficient security boundary. The execution service must enforce session-principal permissions, revision fences, structured action argument validity and required action-specific approvals **outside** the model.
- **False but plausible governance facts** such as forged review approval, invented architecture-policy exceptions or outdated deployment runbooks may not look like prompt injection. A matching SHA proves the quote appeared in a source, not that its claimed approval is current. Resolve against real review records, Git revision and effective permissions; never promote or publish solely because retrieved prose instructs it. Without authoritative records, show the claim as unverified/conflicting and prohibit side effects.

**Not yet verified:** end-to-end malicious-document-to-agent redirection, tool-argument contamination, exfiltration of restricted context, false approval/publication claims, revocation and revision changes after retrieval, benign technical-runbook false positives and classifier bypasses. Measure **both attack success and legitimate task success**; refusal of every instruction is not a useful solution. Exercise sandboxed test review IDs and mock Git/workspace writers, never real credentials or unauthorized publication. Log executor authorization decisions, source SHA/spans, principal, policy revision, tool/action and denial reason without exposing sensitive payloads.

**Required status:** OPEN SECURITY DESIGN/TEST ITEM (CRITICAL before autonomous tool integration); not a confirmed production exploit or a claim of a banking integration.
